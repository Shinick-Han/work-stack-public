# Disposable Work Stack dogfood fixture — source-only smoke

This guide launches the **source checkout** against a **synthetic fixture**
created by `scripts/create_dogfood_fixture.py`. It is not a copy of a personal
SSOT. Unit tests in `tests/test_dogfood_fixture.py` prove projection, links,
status, refusal, and reproducibility. They do **not** claim full UI acceptance;
that happens later on the integrated source.

## Format distinction (do not silently migrate)

| Option | What it is | KR linkage |
| --- | --- | --- |
| `--format v3` (default) | Historical schema-3 fixture with nine documents, derived from disposable `WorkStack` / `Store` staging | Optional scoped `key_result_refs` **are** admitted |
| `--format v4` | Separate experimental conversion of a v3 source that **never** persisted `key_result_refs` | Experimental v4 **has no** that field and refuses the patch |

Do not invent unsupported v3 fields. Do not convert a v3-with-refs store to v4:
product migration refuses `key_result_refs` (`SEMANTIC_PARITY_MISMATCH`). The
v4 option is a distinct dataset, not a silent upgrade of the v3 fixture.

## Create the disposable fixture

`--out` is **required and must be an explicit absolute path** (a leading `~` is
expanded first, so `~/scratch/dogfood` is accepted). Relative paths are refused
before anything is resolved, so the generator can never depend on the shell's
working directory.

The script refuses, before any path resolution, `Store` construction or `mkdir`:

| Refusal code | Cause |
| --- | --- |
| `relative_destination` | `--out` is not absolute after `~` expansion |
| `non_literal_destination` | `--out` contains a `..` segment |
| `live_ssot_destination` | `--out` is or sits under configured `WORK_STACK_HOME` (both lexical and resolved paths), `~/WorkStack/SSOT/main`, `%LOCALAPPDATA%\WorkStack\data`, or `~/.local/share/workstack` |
| `symlink_or_reparse_destination` | `--out` itself is a symlink, junction, or other reparse point |
| `symlink_or_reparse_ancestor` | any **existing ancestor** of `--out` is a symlink, junction, or other reparse point — even when its target is outside every known default SSOT location |
| `destination_not_a_directory` | `--out` exists and is not a directory |
| `existing_nonempty_destination` | `--out` exists and already contains entries |

Pass the real, unaliased path: an aliased ancestor is refused rather than
silently followed. The script does not mutate installed app configuration and
does not launch or restart Work Stack.

Write only under a throwaway evidence or test root:

```text
python -I <checkout>/scripts/create_dogfood_fixture.py --out <absolute-empty-or-absent-dir> --format v3
```

Generation uses private temporary staging and writes only the historical
documents to `<out>`. Before launching the source app, pin its runtime away
from the installed app:

```text
set WORK_STACK_RUNTIME=<out>\.dogfood-runtime
```

On POSIX:

```text
export WORK_STACK_RUNTIME=<out>/.dogfood-runtime
```

## Exact source-only launch

Do **not** use an installed shortcut, `--seed-demo`, or the live SSOT.
Work Stack 1.0.8 upgrades the generated schema-3 collection to schema 5 when
opening it, adding `reports.json` and a verified pre-migration backup. Keep a
separate generated copy if the experiment requires an unchanged v3 authority.

```text
python -I <checkout>/run_work_stack.py --data-dir <out> graph serve --host 127.0.0.1 --port 8765
```

`<out>` must already have been generated by the step above; the launch step
never creates the fixture. Open `http://127.0.0.1:8765/` in a local browser.
Stop the process to restart against the same `--data-dir`.

## Five-minute human smoke

Budget about five minutes. Record pass/fail only; do not copy Task bodies into
shared evidence.

1. **Empty → nonempty.** Use **two** absent destinations, `<empty>` and `<out>`.
   Initialize `<empty>` first (launch the server against it, or run
   `maintenance initialize`) and confirm the board/graph is empty, then stop
   the process. Now generate the v3 fixture into `<out>`, a **second, still
   absent** destination, and launch again with `--data-dir <out>`. Compact
   outcomes must appear: two Objectives (`Dogfood compact outcomes`,
   `Dogfood review and context`) and three Tasks.

   Do **not** generate into `<empty>`. Initializing or launching writes store
   files there, and the generator then correctly refuses it as
   `existing_nonempty_destination`. For any one directory, generation comes
   before the first launch; that refusal is a safety property and is not to be
   weakened to fit this guide.

2. **Completed hiding / reveal.** Default view hides `Done prerequisite`.
   Select `Blocked successor` (depends on that done Task). The prerequisite
   context should classify it as completed/hidden and offer reveal. Reveal
   shows the done Task; clear reveal hides it again. Do not expect this from
   fixture unit tests.
3. **Selected Task without prerequisites.** Select `Independent selected task`.
   It has no dependencies. Shared Context shows the note
   `Shared dogfood context` on `Blocked successor` and the compact Objective.
4. **Observable review checkpoint.** Daily Review / worklog for 2026-09-05
   shows one entry on `Independent selected task` with the recorded done/next
   items.
5. **Restart.** Stop the source server, start the same command again with the
   same `--data-dir <out>`. The same three Tasks, KR links (v3 only), note, and
   checkpoint remain. Restarting against an already-generated `<out>` is
   expected; only *generation* requires an absent or empty destination. Still
   do not point this process at live SSOT.

Zero-linked KR: `Zero-linked KR with no Task refs` exists under the compact
Objective and has no Task `key_result_refs`.
